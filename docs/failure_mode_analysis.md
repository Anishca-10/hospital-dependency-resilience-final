# Failure-Mode Analysis

_Generated from measured experiment results (`data/results/`). Synthetic data and simulated partners only._

| Failure | Cause | Baseline Impact | Resilient Response | User Impact | Recovery |
|---------|-------|-----------------|--------------------|-------------|----------|
| High latency (S2: laboratory ~5000 ms) | Overloaded or slow partner | Visit waits for the slow call (up to the 10.00 s client timeout). Core availability 99.33%, but only 8.00% of visits finish within the 5.00 s SLO | 2 s lab timeout, bounded retries, then breaker opens and later calls fail fast. Core availability 100.00%, 98.33% within SLO | Lab step shows a "temporarily unavailable" message; valid-but-slow lab data is not used (full-fidelity success drops - see report) | Breaker retests every recovery timeout; closes when the partner answers within its timeout |
| Timeout (S5: telemedicine never answers) | Hung connection / partner stall | Each visit blocks for the baseline timeout (twice with its immediate retry) then fails: core availability 8.00%, p95 request latency 20000.00 ms | Per-partner timeout caps each attempt; breaker opens; core availability 100.00%, p95 2000.00 ms | "Telemedicine scheduling is temporarily unavailable. Please try again later." Core visit completes | HALF_OPEN trial after the recovery timeout |
| Intermittent failure (S3: pharmacy 50%; S7: insurance 60%) | Flaky partner, network drops, mixed timeouts and 502/503/504 | One immediate retry only; core availability 77.33% (S3) and 66.67% (S7) | Back-off retries recover some calls (143 retries in S7), breaker trips during bad streaks; core availability 100.00% / 100.00% | Some requests succeed after a retry (status RECOVERED), others get a truthful fallback | Breaker closes after a successful trial |
| Continuous failure (S8: laboratory 502 on every call) | Partner bug / bad deployment | Every visit fails at the lab step: core availability 50.00%; baseline keeps calling the failing partner | 3 consecutive failures open the breaker (50 opens incl. re-opens after failed trials), then fail-fast (100 rejections); core availability 100.00% | Lab results recorded for later sync; honest message | After the partner is fixed: OPEN -> HALF_OPEN -> CLOSED |
| Unavailable partner (S4: insurance HTTP 503) | Outage / maintenance | Every visit fails at insurance: core availability 8.33% (only the healthy warm-up visits succeed) | Retries, breaker opens, fail-fast; core availability 100.00% | Insurance stays PENDING, request recorded for later verification (stored in `pending_actions`); never shown as verified | Pending requests are replayed automatically after recovery |
| Recovery (S6: pharmacy restored; S8: laboratory restored) | Partner fixed / restarted | Baseline resumes as soon as the next call succeeds (mean 0.88 s in S6) | Breaker waits for its recovery timeout, then HALF_OPEN trial; mean 3.82 s in S6 to first full success | Brief extra period of fallback after the partner is back (deliberate protection against flapping) | CLOSED after a successful trial call |
| Invalid request (HTTP 400 / validation) | Caller error | Baseline propagates it as a failed request (no fallback, no classification) | Not retried, no fallback, does not trip the breaker; user is told the request was rejected | Must correct the request | n/a |

## Notes
- Numbers come from 5 seeds x 60 visits per scenario and mode; see `docs/experiment_report.md` for latency, retries, timeouts and error analysis.
- Resilience has costs: retries and back-off add latency before the breaker opens, and recovery is slower than the baseline because the breaker deliberately waits before testing a partner.
- The fallback never reports success for an operation that did not happen. Insurance eligibility is never reported as confirmed while the partner is unreachable.
